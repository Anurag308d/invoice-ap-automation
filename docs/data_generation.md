# Synthetic data generation plan

Status: Stage 1 specification. The exact allocation is already implemented and tested
(`invoice_ap/generator/allocation.py`, `tests/test_allocation.py`). The generator that uses it is
Stage 2. Every count in this page comes from code: the tables in section 4 are generated by
`python -m invoice_ap docs`, and a test fails if they go stale.

## 1. Principles

1. **Parents before children** (assignment steps 2 and 3): reference data, then vendors and their
   status history, then POs and PO lines, then receipts, then invoices, then documents and events.
   Every child references an existing parent ID.
2. **Exact counts, seeded placement.** Integer arithmetic fixes every total, category and
   sub-scenario count. The seeded RNG decides only *which* PO, vendor, SKU, date or channel gets each
   slot, never *how many*.
3. **Valid baseline first, then labelled injections** (step 5). Every invoice slot starts as a clean,
   fully consistent invoice. Then the slot's sub-scenario applies one documented mutation and records
   its intended label set. No unrelated row is touched.
4. **Derived values are computed, never generated** (step 6): line amounts, tax, totals, balances,
   cumulative receipts, receipt types, current statuses and due dates. The only exceptions are the
   labelled defects whose point is that a printed value is wrong.
5. **Labels come from rules** (rule 5). The oracle applies the documented policy to the true data.
   Generation asserts `oracle labels == intended labels` for every invoice and fails loudly
   otherwise. No label is ever drawn at random.

## 2. Parameters and command

| Parameter | Default | Notes |
|---|---|---|
| `--seed` | `20261022` | Master seed; every random stream is derived from it. |
| `--scale` | `starter` and `full` | `full` = factor 1, `starter` = factor 1/10, or any factor in (0, 5], e.g. `0.25`. Same code path. |
| `--policy` | `config/ap_policy.toml` | Tolerances and rules used by the oracle. |
| as-of date | `2026-10-22` | From the policy: a fixed past snapshot date. No completed event lies after it (section 9). |

Commands:
- `python -m invoice_ap generate --scale full --seed 20261022` writes `data/full/`; starter takes
  about 0.2 s and full about 2.5 s.
- `python -m invoice_ap validate --quick --scale full` re-runs the self-checks on the written CSVs.
- `python -m invoice_ap plan --scale starter` prints the allocation.

Each build goes through two phases from one plan (ADR-039). The baseline is all clean and must
validate with 0 violations; then the final phase applies the labelled injections. Generated data
is git-ignored until Stages 5 and 6 close (ruling Q3).

## 4. Exact volume and mix allocation

### 4.1 Algorithm

**Targets.** `target = round_half_up(full_value x factor)` for vendors (300), POs (1,500),
PO lines (2,200), receipts (1,800) and invoices (2,000).

**Apportionment.** Every split uses the Hamilton (largest-remainder) method in exact integer
arithmetic. Ties go to the earlier item. A minimum of 1 per bucket is then enforced by moving single
units from the largest bucket. The full-scale counts are the weights, so the full scale reproduces
them exactly and smaller scales stay proportional. If a scale is too small to give every
sub-scenario at least one invoice, the code raises an error instead of silently dropping a case.

**Categories.** Invoices are apportioned over the eight categories of Table G2. The five named
categories keep their exact assignment shares: 10, 8, 5, 4 and 3%. The two extra required edge
cases ("invoice total differs from line sum" and "invoice date before PO date") are carved out of
CLEAN at 1% each. Degraded scans that must go to capture review form CAPTURE_REVIEW, carved out at
0.5% (ADR-017). CLEAN is therefore 1,350 (67.5%), transparently below the "~70%" target and above
REV's floor of 1,340 (ADR-005, rulings Q1 and Q2). Each non-clean category is apportioned over its
sub-scenarios (Table G6).

**Populations.** Duplicates are extra documents; they have no slot of their own. Non-PO originals
are `round_half_up(5% x invoices)`. PO-backed originals are invoices minus duplicates minus non-PO
originals, which gives 1,800 at full scale.

**PO archetypes.** Each PO follows one fulfilment pattern (Table G4). The archetype counts solve
three linear identities exactly:

```
POs:       n11 + n22 + n33 + n21 + n12 + n01 + n10 + n00 = POs               (1,500)
receipts:  n11 + 2 n22 + 3 n33 + 2 n21 + n12 + n10       = receipts          (1,800)
invoices:  n11 + 2 n22 + 3 n33 + n21 + 2 n12 + n01       = PO-backed originals (1,800)

n01 = missing-receipt invoices                                  (80)
n12 = max(1, round_half_up(POs / 150))   one delivery, two invoices (10)
n21 + n10 = receipts - PO-backed originals + n01 + n12  -> split in half   (45 + 45)
n00 = round_half_up(4% x POs)        open POs                    (60)
n33 = round_half_up(POs / 30)        three-delivery POs          (50)
n22 = PO-backed originals - POs + n10 + n00 - 2 n33 - n12         (295)
n11 = PO-backed originals - n01 - n21 - 2 n22 - 3 n33 - 2 n12     (915)
```

Every count must be >= 0; otherwise generation fails.

**Slots.**
- Each A11 PO gives one S11 invoice slot.
- Each A22 PO gives a partial first invoice and a second invoice (slot S22_2 when a scenario needs
  it, otherwise a clean final invoice).
- Each A33 PO gives two partial invoices and one final invoice.
- Each A21 PO gives one consolidated invoice over two receipts: one invoice line, two GRN lines.
- Each A12 PO gives two invoices that bill its single delivery in parts: one GRN line, two invoice
  lines. Together with A21 this exercises the N:M bridge in both directions.
- Each A01 PO gives one missing-receipt invoice.

Anomalies take their slots first. The remaining S11 slots form the clean single-delivery pool,
which is apportioned over the clean sub-scenarios. The true-negative pairs are reserved first
(5 pairs at full scale, at least 1 pair at any scale). `C-SPLIT-PARTIAL`, `C-SPLIT-FINAL` and
`C-CONSOLIDATED` follow directly from the archetypes. The code asserts that the clean slots add up
to the CLEAN category count.

**PO lines.** The full-scale histogram (1,090 / 260 / 80 / 35 / 15 / 10 / 5 / 5 POs with 1-8 lines)
is the weight vector. At any scale it is apportioned over the POs, keeping at least one 1-line and
one 8-line PO when the total allows. A deterministic repair then moves one PO at a time to the
adjacent line count until the line total is exact. Feasibility check: POs <= lines <= 8 x POs.
Which PO gets which line count is a seeded shuffle.

## 5. Distributions (realism, Evaluation Focus a)

Parameters live in `invoice_ap/generator/params.py`. Every build writes the realised values to
`reports/distribution_summary.{json,md}`, the evidence for realism. Examples at full scale:
- the top 20% of goods vendors place 77.7% of POs and 88.1% of spend;
- median line net ranges from 27,946 (canteen) to 198,224 (IT hardware);
- receipts arrive every month from January to October;
- every scenario category is spread across all ten intake deciles.

| Aspect | Planned distribution |
|---|---|
| Vendor activity | Zipf-like weights `1,000,000 // rank` over a seeded vendor ranking, so roughly the top 20% of vendors carry 70-75% of POs. Tiers STRATEGIC / CORE / TAIL = 10 / 30 / 60%. |
| Vendor segments | 90% GOODS (receive POs) and 10% SERVICES (non-PO invoices only). |
| SKU catalogue | `max(60, round_half_up(PO lines x 2/11))` SKUs (400 full, 60 starter) over 8 goods categories. |
| Unit prices | Log-normal per category, `median x exp(sigma x Z)`, with Z an Irwin-Hall(12) standard-normal approximation computed in Decimal. Medians (INR): raw materials 180/kg, electrical 850, MRO spares 2,400, packaging 95/box, IT hardware 18,000, office supplies 320/pack, safety equipment 650, canteen supplies 120/kg. Sigma 0.4-1.0. PO price = reference price x U(0.92, 1.08). |
| Quantities | Category ranges in the unit of measure (for example IT hardware 1-30 EA, packaging 50-2,000 BOX); KG and L carry 2 decimals. Boundary scenarios use quantities where 5% is a whole number (20, 40, 100, ...). |
| Tax codes | Mostly GST18; GST5 for canteen, safety and part of office supplies; GST0 and EXEMPT for a few SKUs and services. |
| Lead times | Per category, e.g. canteen 1-3 days, IT hardware 7-28 days; receipts land on business days. |
| Deliveries | Partial first delivery 40-70% of the ordered quantity; split deliveries 5-20 days apart; over-receipt 1-5% (inside tolerance) or 6-20% (outside). |
| Dates | All completed events fall inside 2026-01-05 to the as-of date 2026-10-22. POs are on business days from 2026-01-05, with mild quarter-end peaks (March, June, September). Late POs are mostly open (A00) or received-not-invoiced (A10), so their events still fit before the as-of date. Invoice date = delivery date - 3 to + 7 days. Channel delay: PORTAL/EDI 0-1 days, EMAIL 0-3, SCAN 3-8. Intake closes 2026-10-21. Above 95% of business events fall on weekdays. Due dates, SLA dates and scheduled payment dates may fall after the as-of date. |
| Payment terms | NET15 / NET30 / NET45 / NET60 = 10 / 45 / 30 / 15% of vendors. |
| Channels | By tier: STRATEGIC mostly EDI or PORTAL, CORE mostly PORTAL or EMAIL, TAIL mostly EMAIL or SCAN. All four channels appear at both scales. Sender metadata is channel-realistic (ADR-037): PORTAL and EDI carry the authenticated vendor; 10-15% of EMAIL documents arrive from a forwarding mailbox rather than the vendor's remit address; SCAN carries only a mailroom batch ID. A sender-based shortcut would therefore misidentify vendors, which the evaluation would expose (35 forwarded e-mails at full scale). |
| Amounts and approval bands | The product of quantity and price gives a long-tailed gross (median in the tens of thousands of INR, tail above 50 lakh), so all approval bands P1-P4 and N1-N3 occur. Each band and boundary is reported. |
| Non-PO services | Monthly recurring series with a fixed amount on the same day each month (true negatives), plus one-off jobs. |

## 6. Injection mechanics

Each anomaly starts from the clean baseline of its slot and applies exactly one documented change.
Totals are recomputed from the lines unless the defect *is* a printed total.

| Sub-scenario | Mutation applied to the baseline | Invariants kept |
|---|---|---|
| PV-OVER / PV-UNDER | One line's unit price x (1 + v), v in [+2.5%, +15%] or [-10%, -2.5%] | Quantity, tax code and arithmetic consistent |
| PV-BOUNDARY-OUT / C-PRICE-AT-TOL / C-PRICE-INSIDE | PO price chosen so 2% is whole cents; invoice price = PO + 2% + 0.01 / exactly 2% / 2% - 0.01 | As above |
| PV-SPLIT-LATER | Second-delivery invoice price raised 3-12% | First invoice clean |
| QM-PARTIAL-BILLED-FULL | Receipt 40-70% of ordered; invoice bills the ordered quantity | Price exact |
| QM-OVERBILL-RECEIVED | Full receipt; billed quantity = received + 1 to 5% (still <= ordered x 1.05) | |
| QM-CUMULATIVE | Two receipts; second invoice bills more than the second delivery | First invoice clean |
| QM-EXCEEDS-PO-OVERRECEIPT / QM-BOUNDARY-OUT | Receipt and billing at ordered x 1.06-1.20 / ordered x 1.05 + 1 unit | Billed = received |
| QM-EXCEEDS-PO-AND-RECEIVED | Full receipt; billed at ordered x 1.10-1.30 | Two labels expected |
| MR-NO-GRN | A01 PO: no receipt is ever posted | |
| TV-CLOSED / TV-BLOCKED | Vendor gets a CLOSED row (or a BLOCKED window) effective before this invoice date and after all of its other activity | Other invoices of the vendor unaffected |
| TV-TAX-CODE | One line printed with a different valid code; tax computed for that code | Arithmetic consistent |
| TV-TAX-AMOUNT / TV-NPO-TAX-AMOUNT | One line's printed tax off by 0.02 to 5% of the tax | Header totals = line sums |
| TV-VENDOR-PO | The invoice quotes a PO of another vendor in the same category | FK stays valid; label in ground truth |
| ARITH-HEADER-TOTAL | Printed gross differs from the line sum (digit transposition or an omitted line) | Lines consistent |
| ARITH-LINE-EXTENSION | One printed line amount differs from quantity x price | Header = sum of printed lines |
| DATE-INVOICE-BEFORE-PO | Invoice dated 1-20 days before the PO date (retrospective PO) | Receipt after the PO date |
| CAP-DEGRADED-SCAN | Rendered as a SCAN with one required header field unreadable | The true invoice is otherwise clean |
| C-PARTIAL-BILLING | One full delivery billed on two invoices (for example 60% + 40%) | Cumulative billed = received |

## 7. Duplicates

A duplicate document copies an earlier **original** (a non-duplicate, non-degraded invoice whose
intake precedes it). It gets a new `doc_id` and a new `invoice_id` but keeps the vendor's invoice
number:

| Sub-scenario | Content | Channel and timing |
|---|---|---|
| DUP-EXACT | identical | often a different channel, 1-20 days later |
| DUP-EXACT-NORMALIZED | identical except the printed number's case, separators or leading zeros | as above |
| DUP-EXACT-NPO | identical copy of a recurring non-PO invoice | the detector must pick the right month |
| DUP-NUMBER-REUSE | same number, but a different date and amount (a corrected re-bill) | - |
| DUP-CONTENT | same vendor, date, amount and PO, number altered (for example a `-R` suffix) | - |

Duplicates never consume receipt quantity. The ground truth stores the expected original in
`expected_duplicate_of`.

## 8. Ground truth

`ground_truth/ground_truth.csv` and `ground_truth.json` hold one row per invoice, and
`ground_truth_line.csv` holds one row per invoice line (columns in the
[data dictionary](data_dictionary.md#ground_truth)). Key fields:
- scenario category and code, and the edge cases demonstrated;
- intended vs oracle issue labels (asserted equal);
- the primary issue, blocked flag and match status;
- the expected duplicate original, assigned roles and queues;
- the approval band and levels;
- the final status at the as-of date, payment readiness, and the due and scheduled dates;
- the oracle rule IDs, the policy version and a readable description.

`ground_truth.json` wraps the same rows with metadata: seed, scale, policy version and counts. The
ground truth is written to its own folder. It is never an input to the engine.

## 9. Determinism rules

- Sub-streams: `random.Random(int.from_bytes(sha256(f"{seed}:{name}").digest()[:8], "big"))` per concern
  (vendors, skus, pos, receipts, invoices, injections, duplicates, intake, rendering).
- Only integer draws (`randrange`, `shuffle`, integer-weighted choice) plus Decimal arithmetic.
  No `math.exp`, `random.gauss`, `lognormvariate`, wall clock or `uuid` (banned by a test).
- Everything is iterated in sorted ID order; ties are broken by ID.
- Output is byte-stable: UTF-8, `\n` line endings, fixed column order from the spec, decimals as
  canonical strings, JSON with `sort_keys`. Stage 5 proves this by building twice, with
  PYTHONHASHSEED 1 and 2, and comparing SHA-256 checksums.
